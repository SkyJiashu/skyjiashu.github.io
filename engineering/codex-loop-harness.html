Task-scoped AI collaboration, with explicit ownership and recorded evidence.

A public collection of collaboration rules, templates and project-initialisation scripts. It defines how architecture, coordination and implementation roles hand work over, and which artefacts support acceptance.

View repository ↗

The engineering problem

A conversation saying “done” is not the same as an inspected change. The toolkit makes Git, task records and reports the documented sources of truth, rather than relying on chat history alone.

Separate responsibilities

The documented roles distinguish architecture decisions, coordination and acceptance, and task-specific implementation. Changes and review outcomes remain attached to identifiable work.

Make completion explicit

The task specification separates submission, review, rework and completion. A completed task means the review has passed and the change has been merged, not merely that an implementation session has stopped.

A task’s normal path

  1. Pending
  2. Ready
  3. Dispatched
  4. Acknowledged
  5. InProgress
  6. Submitted
  7. InReview
  8. Completed

Rework loops through implementation and review. Blocked or repeatedly failing work follows a documented escalation path. This is a summary of the repository’s protocol, not a claim that a hosted service enforces every transition.

Inspect the evidence

  • Repository overview and project initialiser ↗Role definitions, directory layout, source-of-truth rules and the documented setup command.
  • Task state machine and review protocol ↗Authoritative states, transition paths, submission handling and stop conditions.

Scope & limitations

This is a rules-and-scaffolding toolkit, not a commercial orchestration platform. The public materials describe the intended workflow; they do not establish production adoption, unattended-operation guarantees or benchmarked reliability. Runtime enforcement depends on the implementation that uses these rules.
